# macOS helper: build, install and validate

Version 0.12.26 source support is implemented. No signed PKG has been built or published from the Windows development environment. Do not advertise a tested Mac release until the acceptance checks below pass on both architectures. Existing Windows MSI/update assets are independent.

## Layout and security

- The common XPI retains `mail-ai-assist@lvbeck.github.com`, `local.mail_ai_assist`, and the existing permissions. No Experiment APIs are introduced.
- A system-wide PKG installs into `/Library/Application Support/MailAiAssist`, with the native manifest at `/Library/Application Support/Mozilla/NativeMessagingHosts/local.mail_ai_assist.json`. The absolute launcher path and executable permissions are generated by the package builder. The per-user Thunderbird manifest path, if registering manually, is `~/Library/Mozilla/NativeMessagingHosts/` (not Firefox's user path).
- The helper runs as the Thunderbird user. Mutable data lives in `~/Library/Application Support/MailAiAssist`; launch.sh sets umask 077. Installation never copies user credentials or migrates Windows data.
- A signed Swift bridge uses Security.framework to retrieve/create a per-user 256-bit encryption key in Keychain. Node uses AES-256-GCM with a random nonce and application-specific authenticated data for credential files. Secrets pass only through the child process pipe, never arguments or logs. Keychain authorization failure fails closed. An existing credential read never silently creates a replacement encryption key. Sign-out/removal deletes credential files/entries; the encryption key itself remains for other providers.
- Use a stable Developer ID identity and bridge identifier across upgrades so Keychain access remains stable. Windows DPAPI files cannot be imported as Mac credentials: sign in again and re-enter keys.
- Folder picking uses NSOpenPanel; Finder selection and app opening use NSWorkspace. No GUI scripting, Accessibility automation or automatic attachment/upload is used. The custom app field accepts an absolute `.app` directory. Known app bundle IDs are candidates; verify the installed ChatGPT/Codex editions and use a custom app path if needed.

## Build prerequisites

Use macOS 13+ with Xcode Command Line Tools (`xcrun swiftc`, the macOS SDK, `pkgbuild`, codesign and notarytool), Python 3.10+, and Node.js 22+. The configured target is macOS 13; the bundled Node release may impose a newer minimum, which must be checked before distributing. No npm dependencies are needed to compile the helper or package the XPI. The root npm lockfile pins the optional icon tooling; use `npm ci` only when regenerating icons.

Download the official Node macOS archives for BOTH darwin-arm64 and darwin-x64 from https://nodejs.org/en/download/archive and verify their official checksums/signatures. Supply each extracted archive (containing bin/node and LICENSE) separately. Do not use a Windows node.exe or rely on a user's PATH. Architecture validation uses lipo. Run commands from the repository root. Placeholder paths below must be replaced.

First, compile local test packages (unsigned packages are never eligible for the signed update feed):

```sh
python3 installer/build-macos.py --arch arm64 --runtime /path/to/node-darwin-arm64 --public-key /path/to/update-public-key.pem --unsigned
python3 installer/build-macos.py --arch x64 --runtime /path/to/node-darwin-x64 --public-key /path/to/update-public-key.pem --unsigned
```

The public key must match the publisher key used later by sign-macos-release.mjs. It is not an Apple certificate. No private key is placed in the PKG. For public builds, omit --unsigned and supply Developer ID identities plus an existing notarytool Keychain profile:

```sh
python3 installer/build-macos.py --arch arm64 --runtime /path/to/node-darwin-arm64 \
  --public-key /path/to/update-public-key.pem \
  --app-sign-identity 'Developer ID Application: YOUR NAME (TEAMID)' \
  --installer-sign-identity 'Developer ID Installer: YOUR NAME (TEAMID)' \
  --notary-profile mail-ai-assist-notary
```

Repeat with --arch x64 and the Intel runtime. This explicit signed-build command sends the installer to Apple's notarization service; ordinary source editing and XPI packaging do not. The command never creates a GitHub release or uploads to ATN. Check hardened-runtime/JIT behavior with the chosen Node version. Do not disable Gatekeeper as a distribution solution.

Output: `dist/macos/0.12.26/Mail-AI-Assist-0.12.26-macos-arm64.pkg` and `...-macos-x64.pkg`. The builder refuses to overwrite an existing package. Rebuild after moving an old build to a backup location. System-wide installation requires normal macOS installer authorization. Close Thunderbird before updating and restart it afterward. No login items or background daemons are installed. Sign out/remove keys before uninstalling if desired; uninstall only the helper installation and its matching manifest, never recursively delete the user's data directory.

## Signed updates

The Mac feeds are `helper-updates-macos-arm64.json` and `helper-updates-macos-x64.json`; Windows retains `helper-updates.json` and its MSI workflow. The helper checks at most daily while used. Exact platform/versioned URL, RSA signature, package size and SHA-256 are checked before offering an update, and checked again before opening Installer. A failed/cancelled installer remains available to retry. No automatic elevation, silent package installation or forced Thunderbird termination occurs.

Sign only the final notarized/stapled package. Either sign on Windows with the existing DPAPI key (MAIL_AI_SIGNING_KEY_FILE) after transferring the PKG into dist/macos/0.12.26, or supply an externally managed PEM private-key file on a trusted Mac/CI using MAIL_AI_MAC_SIGNING_KEY_FILE. Never commit or include that private file. Existing signing keys must not be regenerated.

```sh
export MAIL_AI_MAC_SIGNING_KEY_FILE=/private/location/existing-update-key.pem
node installer/sign-macos-release.mjs arm64 /path/to/update-public-key.pem
node installer/sign-macos-release.mjs x64 /path/to/update-public-key.pem
```

This produces per-architecture signed manifests and SHA256SUMS files alongside the PKGs. Publish them only after explicit release approval. Do not overwrite Windows update assets. Unsigned test PKGs for both architectures are available in v0.12.26. They are not Developer ID signed or notarized, and no macOS update manifest is published. Rebuilt PKGs include Mail-AI-Assist.xpi next to setup-guide.html and attempt to open the guide for the logged-in desktop user after installation. Install the XPI manually in Thunderbird and approve its permissions.

## Acceptance checks on real Macs

1. Compile and install each architecture on a clean matching Mac; reject the wrong architecture. Check codesign, notarization, Gatekeeper and execution of the bundled Node runtime.
2. Install the XPI in a clean Thunderbird profile. Verify native-host discovery, launch framing, cancellation, Unicode paths and no startup shell window. Verify an existing user-level native manifest does not shadow the system registration.
3. Sign in, restart, refresh, sign out; save/remove each provider key. Test Keychain locked/denied, concurrent first use and application update. Confirm no plaintext key in files, arguments or logs.
4. Exercise summaries, translations, tags and selected-text preview/confirmation; no automatic sending or broad mailbox scanning. Run portable regression tests separately from the Windows-specific suite.
5. Choose a custom export folder, export TXT/EML, retain quoted/unquoted variants, reveal/select in Finder, drag manually, retain files on close and clear only managed exports. Test folder cancellation and protected Documents/Desktop locations.
6. Test both signed feeds, wrong architecture/key/hash, failed downloads, retry after cancelling Installer, package upgrade and Thunderbird restart. Existing Windows regression tests must still pass.

Portable tests: `node --test tests/macos-support.test.mjs`. Windows regression suite: `node scripts/test.mjs` on Windows. No test should use your real credentials.
